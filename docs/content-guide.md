# 内容与出题规范

## 写给正在解决问题的人

先回答问题，再解释原因。形容词与技术价值匹配，不使用“必问、必会、彻底解决”等无法证实的表述。给出适用条件、反例与验证办法；不要缩短原理来换取口号式答案。

每篇包含：直接回答（summary）、两个以上学习目标、独立可执行示例、原理和工程应用、常见误区或追问、一分钟回答、官方参考资料。长文可使用对照表，流程复杂时再增加原创图示。

## 新增步骤

1. 在 `topics/` 新建具有语义的稳定文件名，例如 `descriptor-precedence.md`。
2. 按现有 front matter 填写标题、摘要、分类、难度、时间、顺序、岗位标签、Python 适用范围、示例、目标和来源。
3. 在 `examples/` 编写相同主题的独立示例与 `.out`，无需网络、真实密钥或本地服务。行为需要确定，避免靠线程调度或极短 sleep 猜测输出。
4. 在 `questions/` 新建同名 YAML。题目 ID 独立稳定，`topicId` 与正文一致。每篇覆盖 mcq、output、debug、oral 四种形式。
5. 有需要时更新路线 ID 清单，再运行 README 中的验证命令。

## 四类练习

- `mcq`：选项对象使用独立 ID，`correct` 引用该 ID。干扰项来自真实误区，避免正确选项总是更长、更完整。
- `output`：包含完整的可执行 `code`、确定的 `answer` 与推导解释。只忽略换行风格、行末空格和首尾空白，保留中间内容差异。
- `debug`：提供有意包含问题的示例、原因与修复检查要点。问题代码不作为成功示例运行。
- `oral`：问题必须可独立理解，评分要点包括概念、条件和例子，不能仅列几个名词。

开放题展示要点后由用户评价“还需复习 / 能说出部分 / 能独立说明”。这些状态不混入客观题正确率。

## 版本与证据

Python 示例的首版验证矩阵为 CPython 3.12、3.13、3.14。若引入更高版本语法或依赖，应更新适用范围、验证矩阵和安装步骤，不能只改正文说明。

GIL 要区分解释器、版本、构建和运行时状态；事务要明确驱动与事务配置；性能结论要说明工作负载和测量方法。不要把默认行为或一次观察写成永久保证。

来源优先采用 Python 官方文档、PEP、框架官方文档和对应源码。独立撰写解释，不整篇搬运第三方材料。新增内容需人工检查引用是否确实支持相关结论。

## ID 维护

标题调整不改知识点 ID。删除或合并知识点前检查路线、练习和旧 URL。题目语义或正确答案发生实质变化时，应更换题目 ID，避免复用旧会话答案；现有累计成绩属于历史记录，不回算成新题成绩。

## 速查与路线维护

速查直接使用 topic 的 summary：先写可独立理解的结论，再给出决定用法的边界；不要写成只有标题含义的导语。代码和输出仍来自 examples，不要另存速查副本。岗位标签用于强调复习场景；难度按理解机制和边界所需的知识判断。新增知识点至少加入一条适合的学习路线。修改 summary 或示例后，同时检查正文页和对应分类速查页的显示、长行与打印。
