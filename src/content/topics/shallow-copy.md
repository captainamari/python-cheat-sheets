## 先画清对象关系

示例的 `source` 指向一个列表，列表里有一个字典，字典的 `tags` 又指向列表。`copy.copy()` 只创建第一层列表，因此修改浅拷贝中的 `tags` 仍会影响原数据。`deepcopy()` 创建独立的嵌套成员，能隔离本例的内部修改。

直接赋值连外层容器也不复制。列表切片、`list.copy()` 和 `dict.copy()` 通常都是浅拷贝；它们适合只修改外层结构的场景。

## 深拷贝并非复制所有外部世界

`deepcopy()` 使用 memo 记录已经处理的对象，既避免循环引用导致无限递归，也保留原对象图中的共享关系。两个字段原来共享同一个子列表，深拷贝后通常仍共享同一个新子列表。

文件句柄、网络连接、锁等资源不能通过复制内存就获得独立的业务语义。自定义类型也可以实现自己的复制行为，所以需要看类型协议和接口约定。

| 操作     | 外层容器 | 嵌套可变成员 | 典型用途           |
| -------- | -------- | ------------ | ------------------ |
| 直接赋值 | 共享     | 共享         | 明确需要同一份状态 |
| 浅拷贝   | 新建     | 通常共享     | 增删外层元素       |
| 深拷贝   | 通常新建 | 递归处理     | 隔离可复制的数据图 |

## 选择最小复制边界

处理接口参数时，若只需要改变一个配置字段，可以新建字典并替换那个字段。如果要修改嵌套列表，再针对该列表复制。这样成本更容易估计，也能让读者看出修改边界。

性能比较应包括数据大小、嵌套深度和复制频率。不要仅凭一次微基准就决定整个系统无条件深拷贝。

## 面试追问

- 元组一定不用复制吗？元组本身不可变，但成员可能可变。
- 循环引用怎样处理？解释 memo 的作用，而不是声称深拷贝会无限递归。

## 一分钟回答

浅拷贝隔离外层容器，深拷贝递归处理对象图。我要先确认后续代码修改哪一层，再选择复制范围。深拷贝可以处理循环和共享引用，但不能把外部资源自动变成独立资源，也有时间和内存成本。
