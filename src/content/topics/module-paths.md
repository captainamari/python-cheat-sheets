## 核心机制

导入系统沿相应查找路径寻找模块，找到后再结合 sys.modules 缓存复用。工作目录、脚本运行方式、环境变量和安装位置都可能影响路径构成。当前目录里存在 json.py 或 typing.py 之类文件时，代码可能导入它而非预期模块，从而出现属性缺失或循环导入式的错误。

## 放到工程里

定位时先打印或检查模块的 `__file__`、spec.origin 以及解释器路径，确认真实加载来源，而不是立即重装依赖。项目采用明确包布局，通过 python -m package.module 或安装后的入口运行，减少临时修改 sys.path 的需要。虚拟环境还应与实际执行的解释器对应，不能只看 shell 中某个 pip 名称。

## 容易混淆的边界

模块来源未必总是普通文件，内置模块、命名空间包和特殊加载器的元数据可能不同。修改文件名后还要注意已有解释器缓存与运行进程是否重启。随意把项目根目录插到 sys.path 最前面会改变优先级，可能修复一处导入却遮蔽另一依赖，应通过结构和入口解决根因。

## 面试追问

为什么开发目录里运行成功，安装成包后却可能出现不同的导入结果？

## 一分钟回答

我先确认实际解释器和模块来源，再检查路径、同名文件与缓存。稳定的包布局和入口比散落的 sys.path 补丁更可靠。验证既覆盖开发目录，也覆盖安装后的干净环境，避免只在作者机器上导入成功。
